# Server, data, notifications and the HTTP API

Read this before changing the CRM's HTTP routes and errors, migrations, configuration of model services, notifications and the outbox, attachments, companies, the titles responses carry, or how an approval moves between its states.

`database/main/migrations/202609190001_notification_in_app_datetime_tz.ts` retypes the in-app notification plugin's timestamp columns to `datetimeTz`, because the plugin declared them naive but stamped zoned instants and the database layer refused that on read, which broke the notification list; the plugin's own `202609180001_notification_in_app_instant_columns` (in-app plugin 0.2.0-beta.14 and later) now does the same, so ours is executed history that finds nothing to change, and stays because applied migrations are never removed. `database/main/migrations/202609280001_authz_default_access_rule_key.ts` gives the default access plugin's rules table the unique `key` column and renamed resource index that the plugin (0.1.0-beta.5) wrote into its already executed `202608210002_create_default_access_rules` instead of a new migration; without it a database created earlier fails every authorization check reading that table, which denies every non-root user, and the plugin's migration keeps reporting a checksum mismatch, a warning this migration accounts for. `database/main/migrations/202609200001_legacy_epoch_timestamps.ts` rewrites timestamps that older plugin and CRM code stored as epoch numbers (a Date sent through the raw query builder) into ISO instants for the scheduler's sync-lock row and the CRM settings rows, because the scheduler plugin from 0.1.0-beta.2 reads its lock through the repository at startup and the repository refuses the legacy value, so an upgraded deployment could not start; it reads and writes through the raw client, since the query adapter presents such values already converted. The LLM services in `config.yml` are a map keyed by service name (`ai.llmServices.deepseek`, and any other a deployment declares, such as `qwen` or `openai`), and the default's key comes from the environment through `env` in `server/config/ai.ts` (`DEEPSEEK_API_KEY`, kept in `.env.local` in development; another service's key is written in `config.yml`; a service's base URL, such as a proxy's for OpenAI, is set on the Models page, or as `options.baseURL` in `config.yml` before the service is first created), since `config.yml` expands no `${NAME}`; `server/config/ai.ts` is the application's own section (`defineAppConfig`, `CrmAiConfig` with `llmServices: Record<string, CrmModelService>`, whose defaults are DeepSeek alone with its model but no key (Qwen and OpenAI were defaults until 2026-10-21), so a deployment, NocoBase Studio's included, only sets the key, the variable optional (`required: false`, as the mail plugin's push and jobs variables in `server/config/mail.ts` are), since a platform holds back a release whose required variables are unset) now that the AI Employee plugin which owned `ai` is gone, and `server/providers/crm-agents/model-services.ts` creates those services on the Agents plugin's Models page at start when they are not there yet, the only place that plugin reads services from. `pnpm-workspace.yaml` pins `@nocobase/db` to one version for the whole tree; raise that pin together with the template's `@nocobase/db` range on every upgrade, or the direct dependency silently stays on the old version. Notifications are sent through the named in-app Channel `inbox` (`CRM_INBOX_CHANNEL` in `server/providers/crm/index.ts`, configured as `notification.channels.inbox` with `provider: in-app`; a deployment's `config.yml` must name it so), as one complete message per send with a route `target` to the record, which the template's inbox (`client/extensions/nocobase-inbox/`, on `/inbox`) links through the router. Every message the CRM sends is queued in `crmOutbox` by the service itself (`CrmService.queueMessage`, through `notifyApproval`: submission and withdrawal to the approver, decision to the applicant; `notifyRecord` and the comment mentions: a record changing hands, a task's internal participants invited, removed, rescheduled or told of a cancellation, a colleague a comment @-mentions; and `remindTask`: a task about to start, from the reminder pass), keyed so the same message is never queued twice, never to whoever made the change, and not for a record that is gone. The settings' four switches turn each kind off (`notifyApprovals`; `notifyRecordChanges`, a record changing hands and a task's participants told of a change; `notifyComments`, a mention and a reply to a thread, which a stored row from before that left record changes off keeps off; `notifyTaskReminders`; under Reminders, all on by default). These were workflows of the workflow plugin until template 1.0.0-beta.58 stopped enabling the plugin: its client, server and CLI registrations are gone, while the dependency and `server/config/workflow.ts` stay as the template keeps them for an application that opts back in; a database from before keeps the plugin's tables and the old workflows, which nothing runs. The reminder scan and the outbox delivery are the provider's two passes on an in-process timer (`CrmProvider.remindTasks` and `deliverNotifications`, every half minute); they were tried as scheduler-plugin tasks and reverted, because administrators have nothing to act on in a minute-by-minute mechanical pass and the plugin keeps every occurrence forever. The service commits the change first: `CrmService.mutate` runs the callbacks registered through the prepared actor's `after` hook once the transaction has committed, and those queue the messages. Business invariants that must hold with the write (a lead turning `working` on its first task, a won deal's company becoming a customer, closing and completion times, lead conversion) stay in the service's transactions. Attachments nothing uses any more are deleted by the daily scheduler task `crm.file-sweep` (target `app.crm-file-sweep`, 03:00 in the CRM's time zone; `sweepFiles` in `server/providers/crm/file-sweep.ts`): a file no record's attachments and no undeleted comment name is noticed by a pass (kept in the `crmSettings` row `file-sweep`) and deleted by a later one 7 days after that and once 7 days old, its stored file through the drive manager and then its `crmFiles` and `crmFileUploads` rows, since the file plugin's metadata deletion keeps the stored object; a file used again meanwhile is kept, and the removal's confirmation says so. Attachments open in the file plugin's preview dialog (`client/extensions/nocobase-file-component-ui`, the plugin's materialized Registry components: images, PDF, text and Markdown, and Word, Excel and PowerPoint rendered in the browser by `@silurus/ooxml`); `client/components/crm/attachments.tsx` maps the CRM's file rows to the plugin's record shape with the CRM's own content route as `contentUrl`, and that route serves the stored type inline only for what a browser renders safely itself.

Every CRM response that lists or shows records carries `titles` and `names` resolved by `server/providers/crm/titles.ts` for the records it refers to; the client never loads a whole table to label a link, and related records are picked through the search pickers in `client/components/crm/record-picker.tsx`, which page the list endpoint with the same filters the pages use. CRM migrations are checksummed history; do not reformat applied files.

The organisations the CRM sells to are companies (公司): entity `companies`, table `crmCompanies`, the link columns `companyId` and a lead's `convertedCompanyId`, the operation `crm.companies` and the page `crm-companies` at `/companies`. They were accounts until `202610100001_crm_companies`, which recreated the table under its new name (the builder renames neither a collection with supplemental metadata nor a field), moved the link columns and renamed `accounts` in the history, the outbox, the history's values and the demo manifest; a mail entry's `accountId` names its mailbox and stays. An installation from before keeps its permission sets, renamed once at boot like the tasks' (`companyGrants`, marker `crm-companies-v1`); the old addresses `/crm/accounts`, `/crm/accounts/<id>` and its tabs lead to the new ones (`client/pages/crm-legacy-redirect.tsx`), so notifications sent before still open. "Account" still means a person's sign-in, a mailbox (the Mail plugin's accounts) and the demo dataset's users.

The CRM's HTTP routes follow the HTTP API design (`references/http-api.md`), at the root of `/api` with no namespace of their own. The records have one route per object and operation rather than a `/:entity` parameter, `/leads`, `/companies`, `/contacts`, `/opportunities`, `/tasks`, `/approvals` and `/comments`, their standard methods in `records.ts` and their own (capture, merge, conversion, the AI's follow-ups and reviews, a task's outcome, an approval's decisions) in `operations.ts`, each declared with `describeRoute()` and validated with `apiValidator()` against the schemas in `server/routes/schemas/`, the records' built from the object definitions; lists answer `{ data, meta }` (paging, `titles`, `names`, `ai`, at most 100 a page), search is `q` and ordering `orderBy`, a create `201` and a delete `204`. The workspace's own routes are in `workspace.ts`: `GET /workspace`, which every page starts from, `GET`/`PUT /systemSettings`, `GET /demoData` with `POST /demoData/import` and `/demoData/remove`, `/geography/places` and `/geography/subdivisions`, `/search`, `/dashboard` and `/dashboard/:list`, `/decisions` and `/decisions/count`, `/aiAgents/running`, `/aiAgents/:agent` and `PUT /aiAgents/:agent/switches`, `POST /attachments/upload`, `GET /attachments?ids=` and `/attachments/:attachmentId/content`, and `POST /mailTimeline/sync`; the demo dataset's account and mailbox plumbing is `demo-services.ts`. `server/routes/crm.ts` mounts them all as one contribution, with the guard (`context.ts`) installed on those paths alone, and `tests/logic/crm.test.ts` checks that the API document declares every route with valid schemas. Errors follow it everywhere: the services throw `CrmError` with a camelCase code, and the router's `onError` answers it through `apiErrorHandler` as an `ApiError` of domain `crm` (`server/routes/errors.ts`): the reason is the code in UPPER_SNAKE_CASE, a field as a field violation and in `metadata.field`, an upstream model's or plugin's explanation in `metadata.detail`; a state the request may not change (the services' 409s) is `400 FAILED_PRECONDITION`, a concurrent change `409 ABORTED`, an unavailable assistant or a failing model `503 UNAVAILABLE`. The client's `errorCode()` (`client/components/crm/api.ts`) turns the reason back into the code, so the texts under `errors.*` stay keyed as they were. A write needs no header of the CRM's own: the session cookie is `SameSite=Lax`, and API keys and agents' run tokens could not send one.

The Mail plugin's 1.0.0-beta.13 rewrote its already executed `202609030001_create_mail_tables` instead of adding a migration (shorter `key` and `providerSubscriptionId` columns and two foreign keys from cascade to no action, for MySQL and SQL Server), so a database that ran the earlier source keeps the earlier columns and cascades, which behave the same here, and warns of the checksum mismatch at every start until `pnpm nocobase db repair` realigns it, which the person runs, since it refuses without `--force` outside a terminal.

An approval's states are a record lifecycle of `@nocobase/lifecycle` (`server/lifecycles/approvals.ts`, a pilot for the CRM's other state machines; the synced Skill's `references/lifecycle.md` is the library's guide). The state stays in `crmApprovals.status`; the runtime (`server/providers/lifecycles.ts`, `lifecycleRuntimeToken`, one for the application, which `CrmService` is given as `lifecycles` and builds over its own database when it is not, as in tests) writes it, with `statusChangedAt` and `lifecycleVersion` beside it, and logs each transition in `lifecycleTransitions` (its effect runs table, `lifecycleEffectRuns`, is empty while no lifecycle declares an effect; migration `202610130001_crm_approval_lifecycle`, which backfilled `statusChangedAt` and left the rows before it at version 0 with no creation in the log). Only the runtime changes the state: `CrmService.save` creates an approval through `runtime.create()` as a draft and leaves `status` out of an edit, and `CrmService.approvalAction` fires `submit` (from a draft or a withdrawn request), `withdraw`, `approve` or `reject`, whose `set` writes the dates and the decision comment; nothing else may write those three columns, the demo dataset included, which backdates only the submission and decision dates. A transition joins the transaction `CrmService.mutate` opened (`Actor.transaction`, the `@nocobase/db` connection its callback received), so it commits or rolls back with the rest, a plan's rehearsal included. The guards are business rules (only the applicant submits or withdraws, an approver is chosen, only the approver who is not the applicant decides); the permissions stay in `approvalAction` and `save`, which check first and answer in the CRM's codes (`approvalLocked`, `forbidden`, `required`), and `lifecycleRefusal` turns what the runtime refuses into the same, a stale version into `conflict`. The side effects (the messages, the AI's review on submission, the deal's follow-up once the approvals submitted together are settled, retiring a waiting review) still run on `CrmService`'s after-commit path, not as lifecycle effects, since they read `Actor.quiet` and the acting person; so the runtime runs without the jobs dispatcher and sweep, which `server/providers/lifecycles.ts` starts with the first effect or trigger. Removing the demo data deletes its approvals' log; deleting one approval keeps it. `GET /api/approvalLifecycle` (`workspace.ts`, the settings capability's) returns the lifecycle's description, `runtime.describe()`, which Settings → Approval process draws.

Who may be chosen as approver is the lifecycle's one administrator-set parameter, the approver rule (`approverRule`, group `approvers`, a `reviewers` field of `role` and `user` selections; default the `sales-manager` role). Its versions are kept by the library's `StoredLifecycleParameters` in the six `lifecycleParameter*` tables (migration `202610140001_crm_lifecycle_parameters`, under the library's default names, shared by any later lifecycle), under the scope `crm` (`LIFECYCLE_PARAMETER_SCOPE`); the runtime is registered with that store, reads the rule live (no snapshot, so a resubmission after a withdrawal follows the current rule), and logs the version each submission ran under in `lifecycleParameterUsages`. The rule is not checked by a guard: who holds a role and the `approve` capability is not read inside SQLite's one transaction, so `CrmService.users` resolves it before `mutate` opens one (`server/providers/crm/approvers.ts`, `resolveApprovers`: the users it names by role or id who are active and hold `approve`) into each user's `canApprove`, which every picker and `checkApprover` (on saving a draft's approver and on submitting) already read; a request once submitted keeps its approver whatever the rule becomes. `GET` and `PUT /api/approverRule` (the settings capability's) read and save it as `{ roles, users }`, each one selection of its own group so any one is enough; a save names the `revision` it was made from (a newer one is `conflict`, 409) and a `requestId` (sent again, nothing is saved twice), and a rule naming nobody who may approve is refused (`noApprovers`). Settings → Approval process shows the people it names now beside the diagram, above its steps, and edits it in one dialog (`client/pages/settings/approval-flow/approvers.tsx`: `ApproverRuleSummary`, its Edit button, and `ApproverRuleDialog`, saving through `PUT /api/approverRule` and showing the version and who set it), opened from that summary or from the diagram itself: the page passes the lifecycle diagram a `configuration` offering the `approvers` group's `approverRule` alone, so the submit step and the states it leaves (Draft, Withdrawn) open it.
