# NocoCRM overview and conventions

Read this before any change to NocoCRM: where the specification lives, the languages code and copy use, the navigation and settings, record links and drawers, phone numbers, the business time zone, field lengths, and the sign-in pages.

Code is written in English: comments, identifiers, literals and the prompts sent to the model. Chinese appears only in translation files — `client/locales/`, `server/locales/` (the AI's labels, headings and conversation titles in `server/locales/crm-ai/`, Chinese first and English second, picked by the AI language setting), the deployment's sales guidance (beside its English version), the demo dataset and the geography names — and in input matching that has to recognise Chinese (a company's legal suffixes, an extension written 转 or 分机); applied migrations are history and stay as they were.

The pages come in ten languages: English, Simplified Chinese, Traditional Chinese (Taiwan), Japanese, Spanish (Spain), Brazilian Portuguese, French, German, Vietnamese and Indonesian, `client/locales/index.ts` and `server/locales/index.ts` listing the same ten (`pnpm nocobase locales check`). English and Simplified Chinese are the source: the CRM's copy is the `wording` pairs in `client/locales/crm/index.ts` (English first, Chinese second); every other language is a file of its own with the same keys, a string each, `client/locales/crm/<locale>.ts` typed `CrmWording` and `client/locales/<locale>.ts` typed `AppResource`, which carries the template's copy translated too since the template ships no such language. A key added to `wording` or to the template's copy fails the type check until every language has it. Traditional Chinese was translated from the Simplified with Taiwan's vocabulary (線索, 商機, 聯絡人, 轉換, 記錄, 示範, 排程任務, 收件匣, 信箱). The others were translated from the English with one glossary per language for the CRM's own terms (Lead, Opportunity, Approval, Owner, Timeline, Nurture, Agent team and the like), kept alike across a language's files: Japanese リード, 商談, 承認; Spanish lead, oportunidad, informal tú; Portuguese lead, oportunidade, você; French prospect, opportunité, vous; German Lead, Verkaufschance, Sie; Vietnamese Khách hàng tiềm năng, Cơ hội; Indonesian Prospek, Peluang, Anda; the word Agent is kept in every language. A string added to `wording` is translated into each of them in the same terms. The calendars take their language through `dateLocale` and `dayPickerLocale` (`client/components/crm/date-locale.ts`), and the server writes to a user in their stored language when it offers it (`servedLocale` in `server/providers/crm/served-locale.ts`: notifications, `crm-notifications` with every language's titles, `{{entity}}` the object's name and `{{record}}` the object inside a sentence for the grammars that need an article). The account menu names the two Chinese by script (see [shell.md](shell.md)). Code that branches on `language.startsWith('zh')` sets punctuation and spacing, right for both Chinese scripts. Not translated: the plugins' own pages (login and users excepted, as the template's copy), which show English in a language they do not ship; the AI's work and its working language, `zh-CN` or `en-US`; the demo dataset; and the provinces' Chinese names.

The CRM is implemented in `client/pages/crm-*.tsx`, `client/components/crm/`, `server/providers/crm/`, and `server/routes/crm.ts`. The pages' addresses start at the application's root, never under `/crm` (since 2026-10-19: mounted at `/crm` on Studio, a lead was `/crm/crm/leads/<id>`): the lists `/leads`, `/opportunities`, `/companies`, `/contacts`, `/tasks`, `/approvals`, a record's page `/<entity>/<id>` with its tab `/<entity>/<id>/<tab>` (one route a kind, `RECORD_ENTITIES` in `client/components/crm/record-route.ts`, which also reads the kind, id and tab from an address, `recordOf`; a single `/:entity/:id` would take `/settings/users` for a record), and `/reports`, `/mail`, `/whatsapp`, `/agent-chat`, `/agent-work`, `/guidance`. Every `/crm/...` address from before, in links, bookmarks and the notifications and mail sent then, leads to its page now (`crm-legacy-redirect`, `/crm/*`, `client/pages/crm-legacy-redirect.tsx`, older names too: `/crm/accounts` to `/companies`, `/crm/agents` to `/agent-work`; `/crm/decisions` keeps its own route and page grant); the server reads a notice's record from either form (`notices.ts`, `removeOrphans`). The file storage's `accessPath: '/crm/files'` is no page and stays. Navigation is declared in `client/routes.ts`: the overview, the inbox, tasks and approvals lead the menu without a heading (the former Action group is gone), the CRM's other pages sit in menu-only groups (Records: leads, opportunities, companies, contacts, then reports; Integrations; Agent team: Agent work, the CRM's four agents on one page, Business guidance, then the Agents plugin's Agents, Skills, Models and Usage), and the application layout's sidebar renders such a group as a labelled `SidebarGroup` with its children always visible (`NavigationMenu`'s `sections` option in `client/layouts/components/navigation-menu.tsx`, an application change to the template's menu), instead of the template's collapsible sub-menu or, collapsed, its popover; and last comes Settings, one entry (`settings` at `/settings`, `client/pages/settings/index.tsx`) whose page holds the pages that configure the CRM as tabs (`LinkTabs` in `client/components/crm/link-tabs.tsx`, which Agent work's tabs use too), at the addresses they had as entries of their own, each tab's route keeping its grant and each tab shown only to whoever it lets open it, `/settings` opening on the first of those; the page draws the title and the tabs, which stick to the top of the layout's scrolling column with a band of the page's ground under their rule, and the tabs' pages keep their description and actions, which `PageHeader` draws on a row under the tabs, its `PageContainer` starting closer to them (`PageFrameContext` in `client/components/page-frame.ts`, an application change to the UI Library's `PageHeader` and `PageContainer`, which `RouteChildPage` clears, so a covering page draws its own heading) (General at `/settings/crm`, 通用, its business defaults and reminders one card under another, each saved by its own card's Save, which sends that card's settings alone and is offered once one of them changed; Demo data at `/settings/demo-data`, 演示数据, the last tab, `client/pages/settings/demo-data.tsx`, the General tab's last card until 2026-10-15, under the same grant; the administration pages the plugins stopped shipping, rebuilt on their APIs in `client/pages/settings/`: Users (`/settings/users`, the users plugin's `UsersClient` with the CRM's role scope, gated by its `user` record type, which only root holds), Permission sets (`/settings/permission-sets`, each row opening two drawers over the list, Permissions at `…/:setKey/permissions/:section` and Members at `…/:setKey/members`, the set's address alone opening Permissions; the Permissions drawer shows the catalog in three tabs by area (Pages, Business operations, Administration; `detail/areas.ts`) over one draft the drawer keeps while the tabs change, saved from its footer, the drawer staying open after a save, asking before it closes with unsaved changes, and refusing a set changed since it was loaded; its editor is the UI Library's `PermissionEditor` (`client/components/permission-editor.tsx`, with application changes: a section's heading may be left out, as an area of one section does, a row without levels spans the levels' column, and a group of bare switches lays them side by side) with the Pages section filled from the route tree, `useRouteTree` in `client/routing/route-context.tsx`, its first group titled Essentials (基础); the set's page with tabs is gone since 2026-10-16), API keys (`/settings/api-keys`, each person's own keys, open to everyone), Approval process (`/settings/approval-flow`, 审批流程, second after General and gated as it is: who may approve, the approver rule an administrator sets (`approvers.tsx`, see the server rules), above the approvals' lifecycle read only, `client/pages/settings/approval-flow/`, drawn by the UI Library's `lifecycle-diagram` from `GET /api/approvalLifecycle` with who takes each step beside it) and Scheduled tasks (`/settings/scheduled-tasks`, the scheduler's schedules with their runs, gated by the page grant `scheduler.schedules` its API checks); their copy is `admin.*` in `client/locales/crm/admin.ts`, their shared components in `client/pages/settings/shared.tsx` and functions in `hooks.ts`, and the assistant's dock is hidden on every `/settings/...` page; the Agents plugin's pages, at the paths the plugin navigates to, `/skills`, `/models`, `/usage`, are in the Agent team section above it, and `/agents`, the coding agents runners report, is routed with no menu entry since the Agents plugin 1.0, its page grant named Runner agents), there being no settings area since template 1.0.0-beta.60, and each entry shows only to whoever its grant lets open it; the sidebar keeps its 16rem width; the brand (`client/layouts/components/app-brand.tsx`) shows the NocoCRM wordmark.

The header (`client/layouts/components/header-actions.tsx`) has no inbox button: the template's (`InboxHeaderButton`, which replaced the CRM's own bell and notification centre in template 1.0.0-beta.56) was removed with `client/components/inbox-button.tsx`, the inbox an entry of the menu's own, right under the overview, instead; the header and keeps the settings link on every surface, marked while settings are shown.

The layout's main column carries the `crm-page-main` class so the assistant panel pushes header and page together, by exactly its 28rem and only from 1280px (`client/styles.css`); it starts closed on every screen (narrower ones show it over the page),. The sign-in pages and the layouts are the template's, translated through the template's own `auth.*`, `status.*`, `shell`, `surface` and `settings` locale keys; the application's own wording lives in the `crm` namespace, `app.title`, `navigation.home` and `loginActivity`. The sign-in pages' right side is the CRM's own (`ActivityPanel` in `client/pages/auth/activity-panel.tsx`, placed by `AuthPage` in `client/pages/auth/shared.tsx` instead of the template's dark NocoBase brand panel): over the split layout's dotted grey, a heading and a line under it, then one sample customer's way from a lead to an opportunity to a closed deal on a record card, the three phases marked above it (`Journey`): the card is first the lead the AI organised out of an email, graded by the AI's follow-up, then, once converted, the opportunity, whose stages fill in as its steps come (a demo prepared, the customer's reply, the AI's follow-up, an approval reviewed and approved), and last the won deal (the lead's statuses and the opportunity's stages each a bar of segments that fill in, `StageBar`); each step appears in the card's timeline, its latest four kept so the card never changes height, the card's foot lights who takes it among everyone taking part (the owner, the four AI agents, the approving manager, the customer; `Participants`) and the tags under the card the capability it uses (AI capture, AI follow-up, pipeline, task preparation, mail, approvals; `Capabilities`), one step every 2.2 seconds, the won card held five before the story starts again, and the whole story shown at once under reduced motion; it is laid over the aside (`absolute inset-0`), so it never stretches the page under the form, and its sample names and figures are the `loginActivity` keys in `client/locales/en-US.ts` and `zh-CN.ts`. The login form's fields and button keep the primitives' heights, as every other form in the application has them in either density preset; the template's taller `h-12` ones (1.0.0-beta.64) were dropped.

A detail page opens the records it links to in a drawer over itself (`client/components/crm/record-drawer.tsx`, state in the `?open=entity/id` query parameter kept by `useRecordDrawerState`, content rendered by the same detail components through `RecordDrawer` in `client/pages/crm-detail.tsx`); the workspace hosts the same drawer for its task and approval cards, loading `RecordDrawer` lazily on the first open so the detail pages stay out of its chunk.

Phone numbers are kept one way (`normalizePhone` in `server/providers/crm/phone.ts`, no imports so the browser may take it): a Chinese mobile as its 11 digits, a Chinese landline as area code, hyphen and number, a number abroad as + and its digits, an extension after a hyphen; `CrmService.save` applies it to every `phone` field, the AI capture to what it fills, and the list search to a typed number as well as the text; `202610030001_crm_phone_numbers` normalised the numbers kept before, with the rules copied into it. The business time zone a CRM starts with, and the one the pages read until the settings have loaded, is US Eastern time (`DEFAULT_TIME_ZONE`, `America/New_York`, in `server/providers/crm/zone-time.ts`, which every fallback takes); a deployment sets its own on the settings' General tab. Field lengths are set once in `server/providers/crm/limits.ts` (255 characters on one line, the width of the text columns, which SQLite ignores and PostgreSQL and MySQL enforce; 30,000 in a long text; 100 items in a list), which `CrmService.save` enforces and the form and inline editors take as their inputs' `maxLength`; it has no imports, so the browser bundle can take it. Record names are drawn through `RecordLink` in `client/components/crm/common.tsx`, which cuts a long name with an ellipsis after one line (two, `lines={2}`, on the board's cards) and shows it whole on hover, so no name wraps into the layout around it, and draws no arrow after it (no link in the CRM does) and, under the pointer, an underline in its own colour (`underline-offset-4 hover:underline`), as the UI Library's links and the settings pages' names in their lists, never a change of colour; draw a record's name through it rather than a bare link. Record links take their props from `useRecordLink`, which falls back to plain navigation where no drawer is provided; every list page's table and board, and the task list, host one (`DrawerHost` in `client/pages/crm-list.tsx`), so the records a row, a card or a task links to (a contact's company, a task's deal) open over the list, while the row's own name still opens its page (its `RecordLink` under `RecordDrawerContext.Provider value={undefined}`), as does its empty space (`openOnRowClick`).

The Vitest configuration resolves the installed `@nocobase/app-client` package rather than the template monorepo alias, so component tests work in this standalone checkout.

Tailwind lists plugin files when Vite starts, so restart `pnpm dev` after installing a plugin, or its classes are missing until then.

See `README.MD` for running the application, demo data, configuration and deployment.

The sidebar's footer (`client/layouts/components/sidebar-footer.tsx`) shows the application's name and version from what the server publishes, `app.displayName` and `app.version`, read from the `package.json` beside the running server, and otherwise from the `package.json` the client was built from (its two fields alone, inlined by Vite), because a host that starts the application elsewhere, as NocoBase Studio's app host does, publishes neither and the footer read v0.0.0.

The company menu checks Better Auth sign-out results before refreshing the session and shows a localized error toast for API or network failures. Preserve this behavior when upgrading the layouts; navigation alone does not revoke a session.

The authorization provider clears the permission snapshot before rendering a new session. Route navigation and page guards subscribe to the authorization revision; preserve these checks when customizing the layouts so account changes and permission updates take effect without a reload. Pending checks hide protected content, and failed checks deny access.

Navigation groups retain their expanded or collapsed state while the navigation tree stays mounted. Selecting a new page expands its ancestor groups without collapsing other groups; users can still collapse the active group manually. Keep this behavior in the application's navigation.

Authentication pages are not plugin-owned: `/login`, `/forgot-password`, and `/reset-password` are application routes declared in `client/routes.ts`; the CRM has no `/register` route and turns the sign-up endpoint off (`emailAndPassword.disableSignUp` in `server/config/auth.ts`), because accounts are created on the Users page, and its login page (`client/pages/auth/login.tsx`) links to registration only while sign-up is on, which it is not, and to the forgot-password page only while the authentication plugin reports self-service reset available (`usePasswordResetCapability`, from `GET /api/authentication/capabilities`, true only with a reset mail configured: `passwordReset.enabled` in `server/config/auth.ts` turns it on, and the mail goes out through the system mailer's `system-email` channel under `notification.channels` in `config.yml`, its password from `SMTP_PASSWORD`; with `SMTP_PASSWORD` set but no such channel, or the channel nested one level too deep, the server refuses to start with that channel "missing a Provider"), as template 1.0.0-beta.64 does, the forgot-password page itself saying so when it is not; the template's `/device` page, which approves a CLI's sign-in, stays.
