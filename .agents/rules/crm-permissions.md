# Roles and permissions

Read this before changing the CRM's roles, permission sets, composite resources, page grants, capabilities, or user deletion.

The Users plugin's own permission-set role scope is switched off in `server/config/users.ts` in favour of the CRM's role scope (`server/providers/crm/user-roles.ts`, registered by `CrmProvider`): one or more CRM roles per user (their grants add up), at least one kept, the last administrator protected. The CRM's administrator is the plugin's own root set (`root`: unrestricted, assignable to users, its last holder kept), so `server/config/authorization.ts` overrides nothing and `roleKey('system-administrator')` is `root`; the two sales roles are the CRM's own sets. An installation whose administrator was the CRM's former `crm-system-administrator` set (once configured as the root set) has its holders moved to `root` and that set deleted once at boot (marker `authz-root-v1`). The plugin's seeded `member` set, held by every signed-in user, carries nothing. The permission model is declared as the plugin's composite resources (its business operations) in `server/providers/crm/resources.ts`: one composite per object (`crm.leads` … view / create / edit / delete, each of view, edit and delete with a `records` data scope chosen from the built-in record access `allRecords`, `recordsIOwn`, `recordsICreated`), placed in the permission workspace's subsection `crm` under Business, plus `crm.sales` (assign, approve, export; the former `manage` capability is translated to `export`, which is all it gated, and the pages decide whether a user may act on a record they do not own from the edit scope the metadata reports as `permissions.<entity>.update.all`) placed with the settings item `settings/crm` in the subsection `crm-capabilities`, also under Business, since the capabilities grant the CRM's own resource type `crm`. The role editor (template 1.0.0-beta.77) shows only what `permissionWorkspaceSelection` in `client/pages/settings/permission-workspace.ts` opts in: the six object composites, `crm.sales` with its four actions, and `settings/crm manage`, which it lists under Configuration permissions; it drops the Administration section entirely, so the Agents and scheduler settings are not offered there. A new composite or action must be added to that selection as well (`tests/logic/crm-permission-workspace.test.ts` checks it). Pages are not registered on the server: every CRM page route declares `authz: page(<route name>)` in `client/routes.ts` (a route without one is root-only), and `crmPages` lists those ids for the sets' page grants. The two sales role sets are built from these (`crmPermissionSet`) and written once at installation by the seed `database/main/seeds/202610040001_crm_sales_permission_sets.ts` (boot never creates or restores a set, so one an administrator deleted stays deleted), and so appear complete and editable on Settings → Roles (`/settings/roles`, the template's prepared page); the plugin expands a resource grant into the collection grants the service authorizes, so `conditions()` and `capability()` are unchanged. Sets provisioned earlier with raw grants are translated once by `translateLegacyGrants` (marker `authz-resources-v1` in `crmSettings`), and grants stored under the former type `resource` (authorization before 0.1.0-beta.10, which no longer reads them, so they would permit nothing) are rewritten once as `composite` grants with the same ids, actions and scopes by `compositeGrants` (marker `authz-composite-v1`), in boot, before the plugin scans the stored grants at start; administrator edits after that are what the page shows and the server enforces, and provisioning never rewrites an existing set. Resource, action and page titles are `{ key: 'crm.…', ns: 'crm' }` (the namespace is the package name, keys under `crm.authz`). The CRM's own capability resource type (`crm`) is a record type registered on `resourceTypes` with `grantBacked()`, declaring `assign`, `approve`, `export` and the administrator's `manage` on `crm/settings`, since an undeclared action is denied even to root; the settings page checks the plugin's `settings/crm manage`, a catalog item `registerCrmResources` adds, because an unregistered settings item is denied to everyone; database grants and decisions name collections without a connection prefix, and a decision's record scope (the database package's filter AST) is compiled into the query builder by `compileFilter` in `server/providers/crm/authorization.ts`.

The CRM's role scope (`user-roles.ts`) gives the users plugin the deletion hooks it requires before deleting anyone: `assertCanDelete` refuses the last administrator and anyone a CRM record still names as owner, creator or approver (`holdsCrmRecords`), and `onDelete` drops the account's CRM roles.
