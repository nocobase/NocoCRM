# Components and styling

Read this before adding or changing a component, a shadcn primitive, a UI Library item, or the application's visual design.

## Imports

Use package-local imports such as `#components/ui/button` and `#extensions/nocobase-auth-forms/form-parts`. `package.json#imports` declares their targets, and `components.json` uses the same prefixes for shadcn generation. Keep directory entry points explicitly mapped to their index files: this application maps `#extensions/nocobase-file-component-ui`, the UI Library source it imports as a whole. An import names the module without its `.js` suffix, which the map adds. Do not add a Vite alias or TypeScript `paths` mapping for these imports.

## shadcn/ui primitives

Use shadcn/ui for UI. The template ships only the primitives its shell and compositions use: `button`, `dialog`, `dropdown-menu`, `input`, `label`, `popover`, `spinner`, `toast` and `tooltip`. Check `client/components/ui/` first; if the primitive is not there, add it from the shadcn registry rather than writing your own. `yes n |` answers "no" when the CLI offers to overwrite a primitive that is already installed; without an answer, a non-interactive run stops at that question. Format the files it created and translate the English a few primitives carry, as [the shadcn guide](../skills/nocobase-app-development/references/frontend/references/shadcn.md) lists; otherwise keep them as the CLI writes them:

```bash
yes n | pnpm exec shadcn add card
pnpm exec prettier --write client/components/ui/card.tsx
```

Build your own components by composing these primitives, and put them in `client/components/`. The template's `DataTable`, `DatePicker` and `Typography` compositions and its `client/pages/reference/` pages were left out of this application when it moved to template 1.0.0-beta.43: the CRM builds its lists, forms and pickers in `client/components/crm/`. The template itself stopped shipping them in 1.0.0-beta.53 and, since 1.0.0-beta.56, has an application compose them from the shadcn primitives, as the next paragraph says. The workspace's tables sort through `client/components/crm/sortable-table.tsx` (TanStack Table's sorting, already a dependency): a header click sorts at once, where the template's `DataTableColumnHeader` asks for a direction in a menu. The list pages use its `SortableHead` too and pass the column as `sort` to the list endpoint, which orders by any column the reader may read (`server/providers/crm/list-order.ts`): up to 20,000 matching records it reads the column for all of them and orders them by what the page shows (an option by its defined order, a relation by its title, text by the reader's locale, blanks last), because the query adapter orders only by a stored column; past that, or for the instants in `DATABASE_ORDERS`, the database orders it. A page below another one — a covering child page, a record's own page — leaves by the header's breadcrumb when its route declares `breadcrumb` or the page declares its trail with `usePageBreadcrumb`, and otherwise by `BackButton` (`client/components/back-button.tsx`) above its heading; never both. The CRM's record pages declare their trail as the object's kind alone (`useRecordBreadcrumb` in `client/components/crm/record-breadcrumb.ts`: "Leads", the record's title being the page's heading; not from the record drawer, whose page beneath keeps its own), since their route has no menu entry and names the object by a parameter, so the route trail would show nothing; they have no `BackButton`.

**Look components up in the shadcn skill.** The development Skill carries the shadcn/ui skill, unchanged from shadcn 4.21.0, in `.agents/skills/nocobase-app-development/references/frontend/shadcn/`. Read [the shadcn guide](../skills/nocobase-app-development/references/frontend/references/shadcn.md) first: it routes to the skill's rules and states where this application departs from them, among others `pnpm exec shadcn` instead of `npx shadcn@latest`, no `shadcn apply` or `--preset`, and create, edit and detail as `RouteDialog` or `RouteDrawer` child routes rather than a `Sheet`. `pnpm exec shadcn docs <name>` gives one primitive's documentation and examples for the Base UI version. For a whole page, start from the worked example that [the example index](../skills/nocobase-app-development/references/frontend/references/example.md) indexes.

## UI Library items

`PageContainer`, `PageHeader`, `RouteDialog`, `RouteDrawer`, `RouteChildPage` and `useRouteOverlay` in `client/components/` come from the NocoBase UI Library, as do the authentication blocks in `client/extensions/nocobase-auth-forms/`, `nocobase-auth-methods/`, `nocobase-auth-split-layout/` and `nocobase-device-approval/` that `client/pages/auth/` composes, the inbox block in `client/extensions/nocobase-inbox/` that `client/pages/inbox.tsx` renders on `/inbox`, and `inbox-badge.ts` (which template 1.0.0-beta.60 no longer ships; kept as the application's own), whose title badge `client/components/crm/waiting-count.ts` uses (the template's `InboxButton` and the header button placing it are gone, the inbox being a menu entry); like the rest of the source, they belong to the application. `yes n | pnpm exec shadcn add @nocobase/<item>` adds another item from the library: a single component lands in `client/components/`, a complete feature in `client/extensions/nocobase-<item>/`. A date field and a list's `DataTable` are the application's own components: compose `DatePicker` in `client/components/date-picker.tsx` from the `calendar` and `popover` primitives, following shadcn's Date Picker guide, and build `DataTable` in `client/components/` from the `table` primitive and `@tanstack/react-table`, following shadcn's Data Table guide. The CLI adds the packages an item or primitive needs to `dependencies`: move the new ones, such as `react-day-picker` for `calendar`, to `devDependencies`, as [where to declare a dependency](../skills/nocobase-app-development/references/dependencies.md) explains for everything client code imports, but leave `@nocobase/i18n` in `dependencies`, where the server needs it, and put back the `^` of its range, which the CLI pins.

## Styling and visual consistency

Style with the semantic Tailwind tokens — `bg-background`, `text-foreground`, `text-muted-foreground`, `border-border`, `bg-primary` — so pages follow the light and dark themes. Do not hard-code colors like `bg-white` or `text-gray-900`; they break the moment someone switches theme.

**Visual consistency is a whole-application property.** Match the surrounding code's spacing, typography, and component choices. If a change genuinely calls for a different look, change the application's design tokens in `client/theme/themes/*.css` so every page moves together. Never restyle only the part you are working on — a page that looks different from the rest is a defect, not a customization.

Whatever may be clicked shows the pointer, the plugins' pages included: a rule in `client/styles.css`'s base layer gives it to buttons, links, tabs, menu items, options, switches, checkboxes, radios, selects, summaries and labels unless they are disabled (natively, `aria-disabled` or Base UI's `data-disabled`), since Tailwind 4 leaves buttons with the arrow; a `cursor-*` utility on an element still wins. The CRM's own colours, tags and form controls are in [the CRM's look](crm-look.md).

The default brand palette and density live in `client/theme/themes/*.css`; shared hover/cursor and Badge geometry live in `client/styles.css`, outside generated shadcn primitives. For semantic status labels, use `StatusBadge` from `client/components/status-badge.tsx` with `neutral`, `info`, `warning`, or `success`; choose the tone by meaning and keep the visible status text. Reuse these shared components and tokens in new pages so template upgrades can carry the design consistently.

**Follow the UI guidelines.** [The UI guidelines](../skills/nocobase-app-development/references/frontend/ui-guidelines.md) set the conventions every page follows, among them the page header and the single placement of the primary action, empty states, row actions behind one "…" menu, dates picked from a `Calendar` in a `Popover` rather than a native date input, and medium-width drawers; the frontend workflow says how much of it to read for a change.

The UI Library's `lifecycle-diagram` (with `flow-diagram` and `flow-layout`, in `client/components/`, as the CLI wrote them, at the version template 1.0.0-beta.75 ships) draws a record lifecycle read only; its `@xyflow/react` and `elkjs` are client packages, so they sit in `devDependencies`, and its `flowDiagram.*` copy comes from `client/locales/system/`, which `en-US.ts` and `zh-CN.ts` spread before rewording the empty, loading and help lines, and which the other languages translate in full.

`client/components/record-link.tsx` (the template's `RecordLink`, which the prepared Users page names users with) carries one application change: under the pointer it takes the primary colour without an underline, as the CRM's own record names do (`RecordLink` in `client/components/crm/common.tsx`); keyboard focus keeps the template's underline and outline. Use it for a record name in a table outside the CRM's record pages; the CRM's pages keep their own.

## File UI source

Template beta.83 tracks `@nocobase/file-component-ui` in `client/extensions/nocobase-file-component-ui/`. Merge its `fileUi` resources into every application locale; the CRM also supplies Korean and Russian. Preserve the CRM Markdown renderer and centred media in the preview content. `FileList` composes the shared `AttachmentList` and forwards custom downloads into the preview toolbar and fallback. CRM record attachments continue to use their existing application components.
